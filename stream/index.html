BetterYTS Stream

Song requests from Twitch, YouTube Live, TikTok (through TikFinity) and this page land in one moderated queue, and play through Pear Desktop. It grew out of PearConnect.

Preview

This is a preview. Streamers create a session from PearConnect Desktop, which gives them a code to share. Nothing here is public until they turn requests on.

Request a song

What it is

One request pipeline for a stream. Every source sends the same kind of event. BetterYTS finds the song itself, applies the streamer's rules, and keeps the queue. A playback destination (PearConnect Desktop with Pear Desktop, for now) takes approved songs one at a time and reports back what happened.

chat / web / bots → /events → rules → BetterYTS lookup → queue → destination (Pear Desktop) → overlays

Set up a stream

  1. In PearConnect Desktop, connect Pear Desktop as usual.
  2. Create a BetterYTS Stream session. You get a code and an owner credential; keep the credential private.
  3. Set your rules (below), mint an overlay link for OBS, then turn requests on.
  4. Share the code. Viewers use !sr song in chat or the form above.

PearConnect Desktop

PearConnect now lives in the BetterYTS repository at apps/pearconnect. Its local queue is still the default. To use BetterYTS Stream instead, set these in .env:

STREAM_BACKEND=betteryts
BETTERYTS_STREAM_CODE=ABCD2345
BETTERYTS_STREAM_TOKEN=<owner, intake or destination credential>

With that set, chat requests go to BetterYTS. Desktop adds each approved song to Pear Desktop, checks that it appeared in the player queue, and reports back. A request that may already have played is never sent again.

Moderation

The owner can mint moderator credentials. Moderators can approve, reject, remove, skip and reorder requests. Only the owner can clear the queue, change rules or mint credentials. Every action is recorded with who did it.

Overlays

Mint an overlay credential to get a browser-source link (/stream/overlay#CODE.TOKEN). It shows now playing, up next and recent songs with requester names, and nothing else. It's read-only, and you can revoke it or let it expire.

API

Base: https://yts.foulfoxhacks.dev/api/stream/v1. JSON in and out. Responses are never cached and never indexed. Credentials are 64-character hex bearer tokens: Authorization: Bearer …. Browsers may only call from this site, and credentialed calls come from apps, not browsers.

ScopeCan
ownerEverything below, plus rules, intake on/off, credentials, clear, end.
moderatorRead the queue; approve, reject, remove, skip, reorder.
intakeSubmit events (chat bots, Streamer.bot, PearConnect).
destinationClaim and report playback.
overlayRead overlay state.

Sessions

POST /sessions                      {minutes: 15-1440, policy?}   → {code, ownerToken, …}  (no browser Origin; 5/min per connection)
GET  /sessions/{code}               public view: accepting, command, destinationOnline
POST /sessions/{code}/manage        owner: {intake?, policy?, minutes?, end?}
POST /sessions/{code}/tokens        owner: {scope, minutes?, label?} → {id, token, expires, overlayUrl?}
POST /sessions/{code}/tokens/revoke owner: {id}

Requests & events

POST /sessions/{code}/requests      website: {id: uuid, name, query}   (6/min per connection; idempotent on id)
GET  /sessions/{code}/requests/{id} website receipt (same connection only)
POST /sessions/{code}/events        intake: canonical event, schema v1
{
  "schemaVersion": "1",
  "eventId": "twitch-msg-8f2c…",
  "eventType": "song_request.submitted",
  "source": { "platform": "twitch" },
  "actor": { "platformUserId": "12345", "displayName": "Viewer" },
  "request": { "input": "Artist - Song", "inputType": "text" },
  "occurredAt": "2026-11-22T12:00:00Z"
}

Platforms: twitch, youtube, tiktok, web, android, vrchat, local. Sending the same eventId again returns the first result.

Queue & moderation

GET  /sessions/{code}/queue         moderator: active, history, stats (received/accepted/rejected/completed), audit, credentials
POST /sessions/{code}/queue/action  {action: approve|reject|remove|complete|skip|reorder|clear, id?, position?, reason?}
GET  /sessions/{code}/overlay  overlay (X-Overlay-Token header): nowPlaying, upcoming, recent

Playback destinations

POST /sessions/{code}/destination/claim   {ready} → {request: {id, media, requester, platform} | null}
POST /sessions/{code}/destination/report  {id, state: playing|completed|failed, code?, message?, outcomeUncertain?}

Claims are handed out one at a time. A claim is saved before the response is sent, and it is never sent again if that response is lost.

Lifecycle & codes

received → resolving → pending_approval → approved → queued → dispatching → playing → completed, or it ends as rejected, skipped, failed or cancelled. Any other move is refused.

Reason codes: usage, invalid_input, forbidden, blocked, cooldown, user_limit, queue_full, duplicate, no_results, unavailable, unsupported, unknown_duration, too_long, live_stream, requests_paused, rate_limited, moderator_rejected, moderator_removed, cleared, destination_failed, outcome_uncertain.
